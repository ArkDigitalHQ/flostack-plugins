# Scaffold plan — tree, order, substitutions

## Placeholders

Apply to every generated file:

- `{{PROJECT_NAME}}` → kebab-case project name (root `package.json` name, README title).
- `{{SCOPE}}` → workspace npm scope, e.g. `@app`. Internal packages become
  `{{SCOPE}}/services`, `{{SCOPE}}/db`, etc.

## Generation order

1. **Root configs** — `package.json`, `pnpm-workspace.yaml`, `turbo.json`,
   `tsconfig.json`, `prettier.config.js`, `eslint.config.mjs`, `.gitignore`,
   `.env.example`. (See `config-templates.md`.)
2. **`packages/config`** — shared tsconfigs everything else extends.
3. **`packages/db`** → **`packages/test-utils`** → **`packages/services`** (with
   the `items` example + test). (See `backend-templates.md`.)
4. **`apps/api`** — context, trpc, router, health + items routers. (See `backend-templates.md`.)
5. **`apps/mcp-server`** (if selected) — items tool. (See `frontend-mcp-templates.md`.)
6. **`apps/web`** / **`apps/web-customer`** (if selected) — supabase + trpc wiring
   and the items page. (See `frontend-mcp-templates.md`.)
7. **`apps/scheduler`**, **`apps/agents/example-agent`** (if selected) — minimal
   health + run stubs. (See `frontend-mcp-templates.md`.)
8. **`apps/docs`** — generate with the official Fumadocs CLI, run fully
   non-interactively (`create-fumadocs-app` with all flags supplied), then adapt it
   to the monorepo and add the documentation-contract stub pages. See the
   **`apps/docs`** section in `frontend-mcp-templates.md` for the exact command and
   post-steps. This runs **before** the root `pnpm install` so the docs app is part
   of the single workspace install.
9. **`supabase/migrations/<timestamp>_init_schema.sql`** — the items table + RLS.
10. **`CLAUDE.md`** — copy this plugin's `templates/CLAUDE.md`, fill placeholders.

## Conditional wiring rules

- If `mcp-server` is **not** selected: skip `apps/mcp-server` and its items tool.
- If `web` / `web-customer` is **not** selected: skip that app and its items page.
- `apps/api`, `packages/{config,db,services,test-utils}`, and `apps/docs` are always
  generated — they are the spine of the vertical slice.
- `pnpm-workspace.yaml` always lists `apps/*`, `apps/agents/*`, `packages/*` (globs
  are harmless even if some are absent).

## The "items" vertical slice

A single trivial domain, threaded end to end, proves the architecture:

- `packages/services/src/items.ts` — `listItems()` + `getItem()` + Zod input schemas. **All logic lives here.**
- `packages/services/src/items.test.ts` — uses `buildSupabaseMock()`.
- `apps/api/src/routers/items.ts` — `items.list` / `items.get` tRPC procedures calling the service.
- `apps/mcp-server/src/tools/items.ts` — `list_items` / `get_item` MCP tools calling the same service.
- `apps/web/src/app/items/page.tsx` — server component calling `api.items.list`.
- `supabase/migrations/*_init_schema.sql` — `items` table with RLS.

## Post-scaffold

```bash
cd {{PROJECT_NAME}}
pnpm install
pnpm typecheck         # must pass — fix before declaring done
```

Then tell the user (do NOT do these for them — they need their own Supabase project):

1. Create a Supabase project; copy the URL + anon + service-role keys.
2. Fill each `.env.local` from the `.env.example` files.
3. Apply the migration (`supabase db push` or paste into the SQL editor) and run
   `pnpm db:gen-types` to populate `packages/db/src/types.ts`.
4. `pnpm dev`.
